# netlab Campus Lab — Build Notes & Future Reference

Multi-vendor campus lab built with **[netlab](https://netlab.tools/)** (installed via pipx at `~/.local/bin/netlab`).
Provider: **containerlab (`clab`)** on Docker. Built/debugged 2026-09-30.

**Current status:** `netlab up` → SUCCESS · `netlab validate` → **4/4 PASS** · lab left running.
Known cosmetic warnings: *"Topology source file(s) have changed since the lab has started"*
(only `validate:` test edits after startup — harmless) and a leftover `netlab.lock` (see Gotchas §4.7).

## 1. Lab overview

```
                 core1 (iol — Cisco IOS-XE L3)
                 /       \
        p2p 10.1.0.0/30   p2p 10.1.0.4/30
              /               \
   dist1 (eos) ============ dist2 (eos)      L2 trunk pair (prefix: False)
   VRRP master blue          VRRP master green   per-VLAN load sharing
        |  \                /  |
        |   \   trunks     /   |             vlan.trunk: [users_blue, users_green]
        |    \  (L2 only) /    |
       acc1 (ioll2)     acc2 (ioll2)          dual-homed L2 access
```

**Addressing (all automatic from built-in pools):**
- loopbacks `10.0.0.0/24 → /32` (node-id based) · core↔dist p2p `10.1.0.0/16 → /30`
- `users_blue` = VLAN 10, `172.16.10.0/24` · `users_green` = VLAN 20, `172.16.20.0/24`
  (SVI host octet = node id: dist1 `.2`, dist2 `.3`, acc1 `.4`, acc2 `.5`; VRRP VIP = `.254`)
- mgmt network `netlab_mgmt` `192.168.121.0/24` (hosts .101–.105)

**Protocol design:** OSPF area 0 everywhere (core↔dist p2p links + dist SVIs) · VRRPv3 per VLAN
(dist1: blue prio 200 / green 100; dist2 mirrored; preempt on) · Rapid-PVST (`stp.protocol: pvrst`)
with root steering (dist blue/green priorities 4096/8192 mirrored; access = default 32768 → dist is root).

**Final validation record (`netlab validate` — all PASS):**
1. `dist1_to_core1` — core1 loopback reachable from dist1 over OSPF (1.0s)
2. `dist2_to_core1` — core1 loopback reachable from dist2 over OSPF (1.3s)
3. `dist1_to_dist2` — dist2 loopback from dist1 **via core1** (no direct L3 link) (1.3s)
4. `dist1_ospf_adj` — dist1↔core1 OSPF neighbor state `full`

Manual smoke checks also confirmed: 2× FULL OSPF adjacencies on core1, VRRP master/backup split per
VLAN on dist (`show vrrp`), STP root priority 4096 + correct root ports on acc1 (`show spanning-tree root`).

- `topology.yml` — the whole design (nodes, links, vlans, groups, validate, image overrides, config attrs)
- `templates/campus-baseline/{iol,ioll2,eos}.j2` — per-device custom config (directory-form template;

## 3. Design decisions & rationale

- **Vendor mapping** — chosen from `netlab show module-support` (authoritative, run it locally):
  - `eos`: vlan ✓ ospf ✓ stp ✓ (stp/rstp/mstp/pvrst) gateway ✓ (anycast+vrrp) → **distribution**
  - `iol`: vlan ✓ ospf ✓ gateway ✓ (vrrp only) **stp ✗ no module** → **core is L3-only**, so no STP needed
  - `ioll2`: vlan ✓ ospf ✓ stp ✓ → **access**
  - VyOS was originally the core but was swapped for iol; note for future: **VyOS has no STP module and
    netlab's vyos vlan template creates bridges without enabling STP → never put VyOS inside a looped
    L2 fabric** (fine as a pure-L3 core/router).
- **`gateway.protocol: vrrp`** (not the netlab default *anycast*) — the gateway module platform table shows
  **Cisco IOS XE supports VRRP but NOT anycast**; VRRP also keeps the design portable if a dist box is swapped.
- **`stp.protocol: pvrst`** — Rapid-PVST+ interoperates between Arista dist and Cisco access; STP domain is
  only {dist1, dist2, acc1, acc2} — core never participates.
- **Image overrides** — netlab defaults (`vrnetlab/cisco_iol:17.16.01a`, `ceos:4.34.2F`, …) are not on this
  machine; the local images are wired in with the `defaults.devices.<dev>.clab.image` pattern (topology-level
  override of netlab settings). Verify in the generated `clab.yml` after `netlab create`.
- **Groups pattern** — `groups.{core,dist,access}` carry `device` + `module` + `config` per tier; node dicts
  only add per-node `vlans` tweaks (VRRP priority + STP priority per VLAN = classic load sharing).
- **`vlan.mode` left at default `irb`** — see Gotcha §4.1; do NOT set `route` on a campus distribution.
- **Dual-homing** (each access uplinked to both dists) creates physical L2 loops on purpose → STP must be
  able to block them; every L2 participant (eos + ioll2) runs pvrst. That is why VyOS/iol were kept out of
  the trunk domain.

## 4. Gotchas log (problems hit, exact symptoms, fixes)

### 4.1 `vlan.mode: route` breaks campus SVIs (router-on-a-stick ≠ SVI switching)
- **Symptom in preview:** dist trunk ports rendered `no switchport` + IP-less `encapsulation dot1q`
  subinterfaces; `interface Vlan10` SVI had an IP but **no L2 backing** → VRRP/OSPF on SVIs would be dead.
- **Cause:** docs ([VLAN module](https://netlab.tools/module/vlan/)) — *mode `route` = routed subinterfaces
  (router-on-a-stick); mode `bridge|irb` = bridged trunks + SVI. **Default is `irb`.**
- **Fix:** removed `vlan.mode: route` from dist node VLANs; default irb renders `switchport mode trunk` on
  parents + SVIs. (The official example's `vlan.mode: route` is for a router-on-a-stick design — do not copy
  blindly.)
- **Lesson:** ALWAYS preview rendered configs before `netlab up` (§5 step 4).

### 4.2 Multi-line IOS banner hangs netmiko → 60s command timeout
- **Symptom:** `ios_config: deploying campus-baseline … command timeout triggered, timeout value is 60 secs`
  on every Cisco node; Arista banner deployed fine (`eos_config … changed`).
- **Cause:** multi-line `banner motd #` / text / `#` puts the IOS CLI into interactive text-collection mode;
  netmiko's line-by-line push never sees a prompt.
- **Fix (current state):** banner **removed** from `iol.j2`/`ioll2.j2` (files kept, empty — a missing file
  would fail the "Find configuration template" task). If a Cisco banner is wanted later, use the single-line
  inline form: `banner motd # message #`.
- EOS banner (`banner motd` … `EOF`) works as-is and is live on dist1/dist2.

### 4.3 IOLL2 rejects `spanning-tree bpduguard default`
- **Symptom:** `% Invalid input detected at '^' marker` during `access-edge` deploy.
- **Evidence:** netlab's own tested template `netsim/ansible/templates/stp/ios.j2` uses
  `spanning-tree portfast default` and **never** pushes bpduguard for IOS.
- **Fix:** `templates/access-edge/ioll2.j2` contains only `spanning-tree portfast default`.
  When real host ports are added, try interface-level `spanning-tree bpduguard enable` per port (untested
  on this image) — if rejected too, rely on portfast + dist-side protections.

### 4.4 `netlab validate` has NO plugin for iol/ioll2 as test *source*
- **Symptom:** `MissingDependency in validate: Cannot find validation plugin for device iol` → tests skipped
  ("results are not reliable"). Built-in plugins live in `netsim/validate/`: eos, frr, linux, cumulus, arcos,
  crpd (+ `bgp/`, `ospf/`, `isis/`, `route/` subdirs) — **no ios/iol file**.
- **Fix:** write tests with `nodes: [<eos or linux>]` as source; iol nodes can still be **targets**
  (`ping('core1')` resolves the target's routable/loopback address, which still proves OSPF end-to-end).

### 4.5 Validation-test naming & plugin-argument rules
- Test names must be **≤16 chars** (same identifier rule as node names):
  `IncorrectType in validate: test name … must be a 16-character identifier`.
- Plugin args may be constants or topology expressions. `nodes.core1.router_id` evaluated to `{}`
  ("OSPF router ID {} is not a valid IP address") → used the constant `ospf_neighbor('10.0.0.1')`.
  Docs use `nodes.dut.ospf.router_id` (module-level field) if you want the expression form.
- Plugin mechanics: `plugin: fn(args)` → netlab runs `show_fn(args)` on the device (output should be JSON
  where applicable) and checks `valid_fn(args)`. `ping` targets resolve via routing utils (loopbacks, not mgmt).

### 4.6 `netlab connect -s` already prepends `show`
- Passing `-s 'show vrrp'` executes `show show vrrp` (device: `% Invalid input`).
  Correct: `netlab connect dist1 -s 'vrrp'`, `netlab connect core1 -s 'ip ospf neighbor'`.

### 4.7 Leftover `netlab.lock`
- After an interrupted (or even completed) run, `netlab create` may refuse:
  *"…remove the netlab.lock file manually and retry"*. Lock = a file in the lab dir.
  **Remove only when no netlab/ansible process is alive** (`ps aux | grep -E '[n]etlab|[a]nsible'`).
  `netlab validate` reads `topology.yml` directly and works despite the lock.
- Related footgun: `pkill -f 'netlab up'` from a shell whose own command line contains that string will
  kill your own shell — use the PID.

### 4.8 Config preview before touching containers (the workflow that caught §4.1)
- `netlab initial -o <dir> --clean` renders every deployment stage per node **without devices**:
  `<node>.initial.cfg`, `.vlan.cfg`, `.ospf.cfg`, `.stp.cfg`, `.gateway.cfg`, `.templates.*.cfg`.
  Stage order matters (e.g. `initial` renders `no switchport`, later `vlan` renders `switchport mode trunk` →
  final state is trunk). Read them before `netlab up`.

## 5. Workflow for building the next lab with netlab

1. **Read the docs** (use these exact URLs — some guessable paths redirect to the homepage):
   - Lab Topology Reference: `https://netlab.tools/topology-reference/`
   - Addressing Tutorial: `https://netlab.tools/example/addressing-tutorial/`
   - VLAN / Gateway / STP module pages: `https://netlab.tools/module/{vlan,gateway,stp}/`
   - Validation tests: `https://netlab.tools/topology/validate/`
   - Custom config templates: `https://netlab.tools/custom-config-templates/`
   - Platforms: `https://netlab.tools/platforms/`
   - Working examples: `https://github.com/ipspace/netlab-examples`
     (used: `STP/examples/09-acc-agg-core.yml`, `VLAN/vlan-access-ospf`, `OSPF/ipv4-only`)
2. **Interrogate the local install** (more reliable than the web for capabilities):
   ```bash
   netlab show devices            # platform support levels
   netlab show module-support     # device × module matrix (vlan/ospf/stp/gateway …)
   netlab show images             # default image per provider
   netlab show providers          # clab/libvirt/external status
   netlab show attributes         # every legal topology attribute
   netlab show defaults paths.custom   # where custom templates are searched
   ```
3. **Write `topology.yml`**, then `netlab create` → fix errors → inspect generated `clab.yml`
   (kinds, images, links) and `hosts.yml`.
4. **Preview configs:** `netlab initial -o /tmp/preview --clean` → read every stage (gotcha §4.1/§4.8).
5. **`netlab up`** (minutes: container boot → readiness SSH check → stages: normalize → initial →
   modules → custom `config` templates). Watch the custom stage — it runs LAST, so earlier green output
   means only the custom templates are at risk.
6. **`netlab validate`** (tests in `topology.yml`; remember §4.4/§4.5) + manual smoke checks (§6).
7. **`netlab collect`** before experimenting with manual changes; **`netlab down`** to tear down.

## 6. Command cheat sheet (verified working on this lab)

```bash
netlab status                          # nodes, images, mgmt IPs, state
netlab connect <node>                  # interactive CLI (core1|dist1|dist2|acc1|acc2)
netlab connect dist1 -s 'vrrp'         # one-shot show (NO 'show' prefix — §4.6)
netlab connect core1 -s 'ip ospf neighbor'
netlab connect acc1  -s 'spanning-tree root'
netlab connect acc1  -s 'run | include portfast'
netlab validate                        # run the 4 lab tests
netlab inspect <expr>                  # transformed data, e.g. `netlab inspect vlans`,
                                       #     `netlab inspect --node dist1 interfaces`
netlab initial                         # (re)deploy all config stages idempotently
netlab create                          # regenerate provider/inventory files only
netlab collect                         # save running configs to configs/
netlab down                            # destroy the lab (keeps source files)
```

**Expected key output:** core1 OSPF → 2 neighbors FULL (10.0.0.2 / 10.0.0.3) · dist1 `show vrrp` →
Vlan10 *Master* (172.16.10.254, local .2, prio 200), Vlan20 *Backup* (master .3) · acc1 STP root
priority 4096+vlanid with root port toward the owning dist.
